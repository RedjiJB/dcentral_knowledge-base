# DC-DOCS-CONSOLIDATION-STD-001: Standard for docs/*.md Maintenance

## 0. Purpose and boundary

This standard governs `docs/*.md` — the hand-authored architecture-spec layer (Consolidator outputs like
`DC-*-RECONCILED-001.md` plus directly-written specs like `DC-COMPUTE-SILICON-ARCH-001.md`) — as distinct from
`knowledge-base/`, which [[DC-PIPELINE-STD-001]]'s eight stages own end to end. `docs/` was outside all eight
stages until Stage 7b/8b (§2 below) were added; this document is what keeps it from drifting back out of sync.

**Golden rule:** `knowledge-base/` is regeneratable pipeline output — never hand-edit it (per the project's
CLAUDE.md). `docs/` is the opposite: every file in it is hand-authored or hand-consolidated, and nothing
regenerates it for you. That means `docs/` has no automatic drift-safety net — the discipline in this document
*is* the safety net.

## 1. What lives in docs/ and what doesn't

| Content | Belongs in |
|---|---|
| A Consolidator pass reconciling 2+ knowledge-base/ source docs on one topic | `docs/DC-<TOPIC>-RECONCILED-001.md`, per [[DC-CONSOLIDATOR-STD-001]] |
| A new architecture spec authored directly (not consolidating existing sources, but extending/filling a gap between them) | `docs/DC-<NAME>-001.md`, following §3 below |
| A registry, index, or standard governing the pipeline itself | `registry/` or `standards/`, not `docs/` |
| Anything Stage 3 would classify and Stage 6 would consolidate from the Claude export | `knowledge-base/`, run through the actual pipeline — never hand-placed in `docs/` |

## 2. Stage 7b / 8b — how docs/ joins the graph

Two scripts extend Stages 7-8 to cover `docs/`, parallel to but separate from the existing `knowledge-base/`
pipeline (different input shape: no YAML frontmatter, no topic membership — `docs/` files reference each other via
plain prose markdown links, `[label](OTHER-DOC.md)`, not frontmatter fields):

```
scripts/build_docs_manifest.py   → registry/docs-manifest.json      (Stage 7b: extraction)
scripts/build_docs_graph.py      → [[wikilink]] Related blocks in-place,
                                    registry/graph/docs/*.csv + load.cypher  (Stage 8b: write)
```

Run **both, in that order, every time you add or edit any `docs/*.md` file**:

```bash
python3 scripts/build_docs_manifest.py
python3 scripts/build_docs_graph.py
```

`build_docs_manifest.py` is read-only (safe to run any time, just to check reference counts). `build_docs_graph.py`
writes an idempotent `<!-- AUTO-GENERATED RELATED START/END -->` block into every `docs/*.md` file — re-running it
always replaces that block cleanly, never appends a duplicate. It uses the `DocSpec` node label in Neo4j (distinct
from `knowledge-base/`'s `Document` label) so the two graphs can coexist in one database without collision.

**This does not retroactively fix `knowledge-base/`'s Stage 7/8 scripts** (`build_manifest.py`,
`build_obsidian_graph.py`, `build_neo4j_load.py`) — those remain scoped to `knowledge-base/d-central/` only, by
design, since that's where the frontmatter/topic-membership schema they parse actually exists. Don't try to point
them at `docs/`; use the parallel `_docs_` scripts instead.

## 3. Writing a new docs/*.md file — the checklist

1. **Check whether it already exists first.** Grep `docs/` for the topic before writing — this repo has already
   accumulated near-duplicate tiering schemes (three separate, unreconciled "Tier 0-3"-style hierarchies exist as
   of this writing — see [[DC-NETWORKING-ARCH-RECONCILED-001]]'s Unresolved tensions and
   [[DC-COMPUTE-SILICON-ARCH-001]] §1's deliberate avoidance of a fourth). A new tiering/naming scheme that doesn't
   check for collision first is the single most common way this layer drifts.
2. **State what it extends or fills, explicitly, in the first section.** Every `docs/*.md` file should open by
   naming the specific gap it closes and which existing docs it extends — not just "this is about X." This is what
   makes Stage 7b's reference-extraction actually find real edges instead of an isolated node.
3. **Link forward, by relative filename, to every doc you extend or reference**, using plain
   `[Display Text](TARGET-FILENAME.md)` links — not `[[wikilinks]]` (those get auto-generated by Stage 8b from
   your plain links; hand-writing `[[wikilinks]]` yourself will just get overwritten by the next
   `build_docs_graph.py` run, since it only reads plain links as input).
4. **Go back and add a "Related work" pointer into every doc you just referenced**, the same session — bidirectional
   linking. Stage 8b computes `referenced_by` automatically from the manifest, so the *wikilink* backlink appears
   without extra work, but a *prose* pointer (a sentence, not just a link, explaining *why* the two relate) in the
   older doc is what actually helps the next reader — the auto-generated block tells them a link exists, not why it
   matters. Do both.
5. **Run Stage 7b/8b (§2) before you consider the work done.** A `docs/*.md` file without a Related block is either
   brand new (fine, just run the scripts) or was edited without re-running them (a drift bug — check
   `git diff` shows the auto-generated block updated alongside your content edit).
6. **Add a row to `registry/DC-REG-001-Master-Registry.md`** in the relevant section — this repo's own registry
   convention (stated in that file's own header) is "each time a new doc gets produced, add a row here before
   closing the chat." Stage 7b doesn't do this for you; it's a separate, manual habit.
7. **If the new doc supersedes or is superseded by an existing one, say so explicitly** — `docs/` currently has no
   `superseded_by`/`duplicate_of` frontmatter mechanism the way `knowledge-base/` does (§4 flags this as a real
   gap). Until that's built, state supersession in prose, in both directions, the same way §1.1's "Related work"
   discipline works.

## 4. Known gaps in this fix — don't assume they're solved

- **No `docs/` frontmatter/dedup schema exists yet.** If `docs/` accumulates enough files that duplicate/superseded
  tracking becomes necessary (it's already borderline, given §3.1's three-tiering-schemes problem), a real
  `docs/`-scoped dedup pass — analogous to [[DC-DEDUP-STD-001]] but for this layer — is a future gap, not solved by
  Stage 7b/8b, which only extract/graph *existing* references, they don't detect *un-linked* near-duplicates.
- **Stage 7b's reference extraction is regex-based on relative filenames only.** A link written as an absolute
  path, a path with `../docs/` prefix, or a link into `knowledge-base/` is deliberately excluded (the last one
  because that's a different, already-covered graph) — but this means a typo'd relative link silently produces no
  edge rather than an error. Check `build_docs_manifest.py`'s printed orphan list after every run; a doc you know
  should reference something else showing up as an orphan usually means a link typo, not a genuine lack of
  relation.
- **Neo4j is never actually loaded** by either the original Stage 8 or this extension — both only ever emit CSV +
  Cypher artifacts for a database that, per `registry/graph/README.md`, doesn't exist yet in this repo. Don't treat
  "wrote N nodes to CSV" as "the graph is queryable" until an actual Neo4j instance is stood up and `load.cypher`
  is run against it.
