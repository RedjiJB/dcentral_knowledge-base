# DC-KNOWLEDGE-LAYERS-001: Additional Layers Over the Archive Tier (Brainstorm)
### Extends DC-MESHSTORAGE-ARCHIVE-001. Exploratory — not everything here is a firm recommendation; flagged where a real open question exists rather than a clean answer.

The archive tier plus the graph layer answer "give me this record" and "what's connected to it." A few more layers are worth naming, and MeshWiki deserves more than a one-line role as "where proposals render."

---

## 1. Semantic/vector retrieval layer

Distinct from the graph layer (DC-MESHSTORAGE-ARCHIVE-001 §4): graph traversal answers *"what's explicitly connected to this record"*; semantic retrieval answers *"what's similar to this, even if nothing links them."* An agent researching a new CVE-equivalent finding has no explicit graph edge to a conceptually related finding from eight months ago in a different coop — only a graph layer can't surface that, a semantic index can.

**Shape:** embeddings generated by an open-weight embedding model on `mesh-ai` (consistent with the open-source-model requirement already established), indexed in a self-hosted vector store, scoped per-tier the same way the graph index and observability index are — local, rebuildable from the archive tier's content, never the source of truth itself. This directly strengthens the "scoped context" step in DC-DAO-AGENT-LOOP-001 §2, which currently names *where* an agent should read from but not *how* it efficiently finds the relevant subset among what could be thousands of prior attestations.

## 2. Wiki-to-attestation verification link

A real gap in what's specified so far: proposals "render into MeshWiki," but nothing yet lets a reader confirm the wiki page hasn't drifted from the underlying attested record. A wiki page is editable prose; an attestation is immutable. Those need to stay verifiably linked, not just related by convention.

**Shape:** every MeshWiki page rendering a finalized proposal or outcome-review displays the content hash of the archive-tier record it's rendering, and ideally a one-click recompute-and-compare so a reader doesn't have to trust the rendering — they can verify it. This is a small addition with an outsized payoff: it's what makes "the wiki is how humans read the record" actually as trustworthy as reading the raw attestation directly, which is the whole point of having a human-readable layer at all.

## 3. Notification / subscription layer

Not a new storage system — a consumption pattern over the event-sourced sync mechanism already specified (004 §1.1: local node writes to its own event log, replicates on next contact). A stakeholder subscribing to "notify me on new security-domain proposals" is just a filtered tail of that same log. Worth naming explicitly as a feature rather than leaving it as an unstated capability of infrastructure that already exists.

## 4. Reuse mesh-bandwidth for hot content, don't rebuild caching

Popular MeshSocial content already gets edge-cached via `mesh-bandwidth` relay so origin nodes don't get hammered (004 §2.7). A widely-referenced past outcome-review or a heavily-trafficked wiki page is the same shape of problem. Worth stating plainly so nobody builds a second caching layer for knowledge content when one already exists for social content.

## 5. Access-log layer — flagged as a real open question, not resolved

Should reads against selectively-disclosed data be logged? There's a genuine tension here worth putting in front of the DAO rather than deciding unilaterally:

- **For:** accountability — if a credential holder queries sensitive data, a record of who accessed what strengthens the same trust model already applied to writes.
- **Against:** an access log is itself a surveillance surface — it tells you who was researching what, which can be more sensitive than the underlying data. Logging every read to preserve accountability can quietly recreate the exact centralized-surveillance problem the selective-disclosure architecture exists to avoid.

No recommendation here — this is a values trade-off for governance to make explicitly, not an engineering default to fall into. If it's adopted, the access log itself should probably be held to the same aggregation-only, no-raw-detail discipline already used for observability and rollout metrics, rather than a literal who-read-what ledger.

---

## MeshWiki, developed further

Beyond "proposals render here" (as already stated across the document set):

- **Not just a proposal viewer — the living taxonomy itself.** DC-TAXONOMY-005 §3 already names this directly: an agent's grounding context should be "this document series" kept in mesh-storage, version-controlled, specifically so agents research against current architecture, not a stale copy. MeshWiki is the natural home for that living document set too, not just finalized proposals — the taxonomy documents this very conversation has been producing are, structurally, exactly the kind of content MeshWiki exists to host.
- **Scoped spaces per governance body**, already specified — worth adding: a **cross-tier index page** at the ecosystem level linking into each coop's space, so a stakeholder or auditor doesn't need to already know which coop owns a given proposal to find it. Small addition, meaningfully improves discoverability at "many DAOs" scale.
- **Revision history as a feature, not just a mechanism.** The existing `revision-history-engine` already tracks edits — surfacing that history directly on finalized-proposal pages (who edited the rendering, when, reconciled against §2's hash-verification) turns an internal mechanism into a visible trust signal.
- **A place for the bounty/advisory output too, not just DAO proposals.** DC-EXPERT-DAO-001 §5's winning bounty solutions and accepted attested findings belong in the same knowledge space proposals do — otherwise MeshWiki becomes proposal-only and expert-network output ends up homeless.

---

*DC-KNOWLEDGE-LAYERS-001 — brainstormed additions to the archive/graph stack: a semantic retrieval layer distinct from graph traversal, a verification link between MeshWiki renderings and their underlying attestations, a notification layer that's really just a consumption pattern over existing event sync, reuse of mesh-bandwidth caching for hot knowledge content instead of a new cache layer, and an explicitly unresolved access-log question left for governance rather than answered by default. Also expands MeshWiki's role beyond proposal rendering to the living taxonomy itself, cross-tier discoverability, visible revision history, and a home for bounty/advisory output.*
